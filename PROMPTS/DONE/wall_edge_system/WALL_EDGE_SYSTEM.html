Diagnóstico do Estado Atual

O sistema de subcubos atual renderiza corretamente geometria e shading, mas o posicionamento das paredes está incorreto. Os subcubos de parede ficam dentro do tile — consumindo área útil — em vez de sentar sobre a aresta entre dois tiles adjacentes.

ESTADO ATUAL — Subcubos centrados dentro do tile. Shading correto, posicionamento incorreto.

Consequências do Problema

  • Tiles com uma parede perdem 1/4 da área útil para subcubos de parede
  • Tiles de esquina (duas paredes) perdem até 2/4 da área útil
  • Quebra o princípio de que a espessura da parede se divide entre os dois tiles adjacentes
  • Divergência visual em relação ao sistema anterior — que funcionava corretamente
REFERÊNCIA CORRETA — Sistema antigo. Paredes laranjas sentam sobre a aresta, dividindo espessura entre tiles adjacentes.
O sistema de coordenadas e toda a lógica de gameplay (A*, guard FSM, detecção) operam no plano de gameplay 256×128 e permanecem intocados. O problema é exclusivamente de renderização no plano de geometria 64×32.
fase 01

Wall Edge Offset prioritário

01 Fundação Geométrica

Offset Direcional por Lado

O sistema antigo implementava 4 tipos de parede (N/S/L/O), cada um com um offset direcional que empurrava o sprite para fora do tile em direção à aresta correta. O novo sistema de subcubos precisa replicar esse comportamento.

Regra de Offset

Cada parede conhece seu lado (N, S, L, O) e recebe um deslocamento de aproximadamente meio subcubo nessa direção, centrando-a sobre a aresta. O valor exato em pixels deve ser calibrado empiricamente durante a implementação.

# Offsets direcionais aproximados (a calibrar) WALL_OFFSET = { "N": Vector2(-HALF_STEP, -HALF_STEP), "S": Vector2(+HALF_STEP, +HALF_STEP), "L": Vector2(+HALF_STEP, -HALF_STEP), "O": Vector2(-HALF_STEP, +HALF_STEP), } # HALF_STEP = SUBCUBE_STEP_PX / 2 = 20.0 px (ponto de partida)
HALF CUBE OFFSET aplicado nos dois segmentos retos. QUARTER CUBE NEEDED aponta o gap de esquina resultante.
01b Corner Fill

Coluna Extra de Corner

O offset direcional resolve as paredes retas mas cria um gap triangular no encontro de duas paredes perpendiculares. A solução é inserir uma coluna extra de subcubos em cada esquina.

  • A coluna extra é composta de subcubos puros — sem asset especial
  • Posicionada com overlapping deliberado: meio subcubo para cada lado, sobrescrevendo as extremidades das duas paredes adjacentes
  • O shading é resolvido automaticamente pelo sistema de iluminação existente — sem lógica de face própria
  • 4 variantes de posição: NW, NE, SW, SE (offsets diferentes para cada direção)
COLUNA DE CORNER (azul) — sobreposição deliberada de meio subcubo para cada lado, preenchendo o gap sem peça especial.
# Offsets de corner (a calibrar) CORNER_OFFSET = { "NW": Vector2(-QUARTER_STEP, -QUARTER_STEP), "NE": Vector2(+QUARTER_STEP, -QUARTER_STEP), "SW": Vector2(-QUARTER_STEP, +QUARTER_STEP), "SE": Vector2(+QUARTER_STEP, +QUARTER_STEP), } # QUARTER_STEP = SUBCUBE_STEP_PX / 4 = 10.0 px (ponto de partida)
Ao restaurar o tamanho e posição dos sprites de parede para o mesmo footprint do sistema antigo, a geometria de coordenadas existente volta a funcionar integralmente — sem necessidade de reescrever lógica de posicionamento.
fase 02

Container System planejado

Renderizar subcubos individualmente a cada frame é inviável à escala de uma sala completa. O Container é a unidade de render que resolve esse problema, agrupando 1 a 64 subcubos em um sprite 2.5D composto e cacheado.

CONTAINER SYSTEM — Subcubos atômicos → parede simples → Container → High Wall (múltiplos containers labelados).
02 Hierarquia de Objetos

Três Níveis de Granularidade

Nível
Descrição
Subcubo
Átomo do sistema. Porta estado individual: lit, broken, visible, shadow_value, audio_semantic. Identificado por wall_XX_subcube_YY.
Container
1–64 subcubos. Unidade de render e posicionamento. Sprite montado via PIL em runtime. Reprocessado apenas quando algum subcubo interno sofre alteração de estado (dirty flag).
High Wall / Objeto Composto
Múltiplos containers com label próprio (ex: wall_28). Permite alterações em batch. Ex: apagar todos os subcubos da wall_28 com uma única instrução.
02b Ciclo de Vida & Estado

Dirty Flag e Event-Driven

Loading

Todos os containers de uma sala são montados e renderizados uma única vez. O PIL compõe os subcubos e gera o sprite cacheado.

Runtime

O sistema não re-renderiza por frame. Um subcubo entra em estado dirty quando recebe um trigger de alteração. O container pai é re-renderizado na próxima janela de TIC.

Triggers de Alteração

  • Luz — mudança de nível de iluminação no subcubo
  • Sombra — projeção de shadow layer atingindo o subcubo
  • Destruição — subcubo removido/danificado
  • Visibilidade/FOW — estado de fog of war alterado
  • Áudio semântico — detecção de som associada à posição do subcubo (gameplay)
Atualização por TIC, não por frame — princípio global do engine. Isso garante que mesmo com centenas de subcubos dirty simultaneamente, o custo de re-render é pago uma vez por TIC, não a cada frame.

Escala de Exemplos

# Containers por complexidade candle: 1×1×1 = 1 subcubo half_crate: 2×2×2 = 8 subcubos full_crate: 4×4×4 = 64 subcubos wall_1t: 1×4×4 = 16 subcubos (parede de 1 tile × altura 4) high_wall: N × containers wall_1t
Beta scope: áudio espacial estéreo por subcubo (som de quebra com informação de posição 3D) está planejado mas fora do escopo atual.

03 Seleção de Textura

Textura por Sessão

No loading de cada missão, uma textura é selecionada seguindo uma hierarquia de critérios:

  1. Temática do cenário (industrial, medieval, hospitalar, etc.)
  2. Tier do jogador — jogadores elite recebem texturas distintas de iniciantes, criando cenários visualmente únicos para cada nível de dificuldade
  3. Convenções de sessão definidas pelo mapa (configurável por designer)

03b Baking

CROP + MULTIPLY

  • CROP — cada subcubo recebe o fragmento da textura correspondente à sua posição dentro do container (mapeamento UV simplificado)
  • MULTIPLY — blend mode que preserva o shading de iluminação do subcubo (top/left/right) enquanto a textura adiciona o material por cima
  • Resultado: subcubo com cor de material × intensidade de face — sem recalcular shading

Destruição Runtime

Cada subcubo carrega seu fragmento de textura baked. Quando é destruído, o fragmento desaparece junto — a textura "vai embora com o bloco", mantendo coerência visual sem nenhum custo adicional de render.

O MULTIPLY é o mesmo blend mode já usado pelo TileOverlay existente (BLEND_MODE_MUL para sombras). A infraestrutura de compositing já existe no engine — o baking system é uma extensão natural.
fase 04

Migração do Sistema Legado planejado

04 Estratégia de Migração

Substituição de Assets, não Reescrita

A migração é cirúrgica. O sistema de coordenadas, os offsets direcionais (N/S/L/O), e toda a lógica de posicionamento de parede permanecem intactos. O que muda é o que está na ponta do ponteiro:

# ANTES tile_position → sprite estático # DEPOIS tile_position → Container primário / secundário

Ordem de Migração Recomendada

  1. Implementar Fase 1 (edge offset + corner fill) com subcubos puros — validar geometria
  2. Encapsular em Containers primários — validar dirty flag e ciclo de TIC
  3. Implementar High Wall (containers compostos) — validar batch updates
  4. Implementar Texture Overlay + Baking — validar CROP + MULTIPLY
  5. Conectar ao sistema de detecção por áudio semântico
O mesmo Container pode ser apontado por múltiplos tiles (instâncias) — objeto idêntico em posições diferentes compartilha o mesmo sprite base, economizando memória de textura.

Glossário e Constantes

Termos do Sistema

Termo
Definição
Subcubo
Unidade atômica visual. 1/4 de tile no eixo horizontal, 1/4 de altura no eixo vertical de render. Portador de estado individual.
Container
Agrupamento de 1–64 subcubos. Unidade de render e posicionamento. Sprite 2.5D composto via PIL, cacheado e atualizado por dirty flag.
High Wall
Objeto composto de múltiplos Containers, com label único. Permite operações em batch (acender/apagar/destruir) a baixíssimo custo.
Wall Edge Offset
Deslocamento direcional aplicado a cada parede para posicioná-la sobre a aresta do tile, dividindo a espessura com o tile adjacente.
Corner Fill
Coluna extra de subcubos inserida no encontro de duas paredes perpendiculares para fechar o gap gerado pelo offset duplo.
Texture Overlay
Textura de material selecionada no loading e "impressa" sobre os Containers via CROP + MULTIPLY. Dinâmica por sessão e tier de jogador.
Baking System
Pipeline PIL que combina o sprite de Container com a Texture Overlay, produzindo o sprite final com material baked por subcubo.
Dirty Flag
Marcador por subcubo. Quando ativo, sinaliza que o Container pai precisa ser re-renderizado na próxima janela de TIC.
TIC
Unidade de atualização do engine INFILTRAITOR. Todas as mudanças de estado (render, gameplay, áudio semântico) são processadas por TIC, não por frame.
Áudio Semântico
Sistema de detecção auditiva de gameplay. Um trigger de estado do subcubo — não emissão sonora. Áudio espacial estéreo planejado para Beta.
